      전국 모든 지자체 현장에 100% 유동적으로 대응하는 범용 시스템으로 완성하기 위함.

1. 하드코딩 현황 및 문제점 요약
--------------------------------------------------------------------------------
- 본 시스템은 엑셀 파일(도로대장_시설물_조사옵션_템플릿.xlsx)을 통해 56개 시설물의
  명칭, 레이어, 색상, 접두어, 제원 옵션을 현장마다 유동적으로 설정하도록 설계되었습니다.
- 하지만 초기 개발 당시 '가로등 집중 조사 앱'에서 출발하여 점진적으로 확장되다 보니,
  일부 주요 시설물(가로등, 표지판, 배수암거, 측구, 석축 등)에 대해 엑셀 설정을 무시하고
  자바스크립트 코드 내부에서 이름을 직접 비교(if-else)하여 강제 조립하거나 해석하는
  '하드코딩 잔재'들이 남아 있습니다.
- 이로 인해 발생하는 부작용:
  ① 엑셀에서 옵션 순서나 명칭을 바꿔도 코드의 하드코딩 분기가 먼저 작동하여 무시됨.
  ② 필드 이름이 엑셀 규격(f_1, f_2)과 구형 규격(type1, spec 등)으로 혼용되어 데이터 유실 위험.
  ③ 특정 시설물 차단 코드 때문에 부시설물이 주시설물로 둔갑하는 버그 유발.

2. 하드코딩 잔재 전수 조사 목록 (코드 위치 명시)
--------------------------------------------------------------------------------

(1) app.js (모바일 현장조사 앱)
  ① 라인 134 ~ 450 (약 500줄):
     - 거대한 구형 FACILITY_CONFIG 폴백(Fallback) 객체 잔재.
     - 엑셀 도입 전 옛날 필드명(type1, lightSource, wing, sump, support 등)이 그대로 존재.
  ② 라인 4503 ~ 4550 (deserializeSpecText 함수 내부):
     - '도로표지', '배수관', '가로등/보안등' 전용 수동 분기문.
     - 엑셀의 f_1, f_2 대신 direction, content, spec 등의 옛날 변수로 값을 쪼개어 넣음.
  ③ 라인 3036 (createPhotoMarker 함수 내부):
     - p.facilityType === '측구' || p.facilityType === '도로' 일 때만 빨간색(#FF0000)
       마커로 고정 칠하도록 시설물 명칭이 하드코딩됨.
  ④ 라인 35 ~ 41 (전역 상태 변수명):
     - pendingStreetlightItem, pendingStreetlightDxfCoords 등 변수 이름 자체가
       가로등(Streetlight) 전용 명칭으로 남아있음 (기능상 동작하나 가독성 저해).

(2) map-editor_v3.js (PC 웹 도면 편집기)
  ① 라인 3570 ~ 3686 (deserializeSpecText 함수 내부):
     - if (fType === '석축') : 석축 전용 4단 분기
     - else if (fType === '과속방지턱') : 방지턱 전용 분기
     - else if (fType === '가로등(보안등)') : 가로등+보안등 10단 역직렬화 전용 파서
     - else if (config.joinFormat) : 배수암거, 측구, 통로박스, 교량 가로*세로 치수 분기
     - else if (fType === '지시표지' || fType === '규제표지' ...) : 표지판 높이/제원 분기
  ② 라인 4459 ~ 4517 (buildSpecString 함수 내부):
     - if (type === '가로등(보안등)') : 가등/종류/재질/형태/광원/높이/암길이/+보안등/...
       순서로 강제 조립하는 50줄의 하드코딩 전개 로직.
     - isSub && (type === '가로등' ...) : 부속 가로등 전용 조립 분기.
     - 라인 4539 : f.label === '암길이' || f.id === 'f_6' 일 때 슬래시(/) 제거 하드코딩.
  ③ 라인 3417 ~ 3455 (normalizeFacilityValues 함수 내부):
     - '기타표지', '지시표지', '규제표지' 등 과거 엑셀 순서 변경 전 데이터 감지 및
       강제 스왑(f_1, f_2 교체) 로직.

--------------------------------------------------------------------------------
3. 향후 단계별 개선 작업 절차 (Roadmap)
--------------------------------------------------------------------------------

[1단계] 엑셀 템플릿(Excel)의 표현력 확장 (코드 대신 엑셀에 규칙 부여)
  - 엑셀 시설물_조사옵션 시트에 특수 규칙 컬럼 추가:
    * 치수 결합 규칙 (예: 가로*세로 곱하기 형태 지원 여부)
    * 복합 부속 전개 규칙 (가로등+보안등처럼 한 줄로 합칠지, 별도 줄로 나눌지)
    * 마커 색상 또는 표시 스타일 지정

[2단계] 엑셀 변환기(convert_excel_to_config.py) 고도화
  - 엑셀에 적힌 특수 규칙을 facility-config.js로 완벽히 추출하여 JSON 구조화.
  - 이를 통해 자바스크립트 코드에서 "if (type === '가로등')" 같은 코드를 쓰지 않고,
    "if (config.joinMultiply)" 같은 범용 속성 검사로 대체.

[3단계] map-editor_v3.js의 수동 분기문 100% 범용화 (단일 엔진화)
  - deserializeSpecText (역직렬화):
    모든 시설물이 config.fields의 순서와 속성(isSupport, isPhoto, 치수형태 등)을
    기반으로 1개의 단일 공통 파서 루프만 돌도록 통일.
  - buildSpecString (조립기):
    가로등(보안등) 등의 특수 조립문을 제거하고, 엑셀에 정의된 필드 순서대로
    공백/생략 규칙에 맞춰 자연스럽게 슬래시(/)로 연결되는 범용 조립기로 통일.

[4단계] app.js 상단의 500줄 구형 폴백 객체 제거
  - window.FACILITY_CONFIG가 존재하면 무조건 그것만 사용하도록 하고,
    상단의 500줄 레거시 객체를 제거하여 단일 소스 원칙(Single Source of Truth) 확립.
  - app.js 내부의 deserializeSpecText 및 폼 바인딩도 map-editor_v3.js와 동일한
    신형 범용 엔진으로 일원화.

4. 안전한 작업을 위한 주의사항 (체크리스트)
--------------------------------------------------------------------------------
- [주의 1] 반드시 평택시 현재 현장의 데이터 작업 및 도면 납품이 완전히 끝난 후 착수할 것.
- [주의 2] 작업 전 전체 프로젝트 폴더를 반드시 다른 드라이브나 압축 파일로 안전 백업할 것.

           캐드 전개 플러그인이 생성하는 레이어명(_T)과 문자가 검수 프로그램의
           기준에 부합하는지 테스트 도면을 통해 최종 확인 필수.
